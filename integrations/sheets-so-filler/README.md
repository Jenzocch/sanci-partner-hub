# 用系統資料填「Form SO INV dan DO-SANCI」的 SO 分頁

> 這份說明寫給 Jenzo 本人操作，**不需要任何程式基礎**。照著順序做，每一步
> 都有明確的畫面路徑。全部做完大約 10 分鐘（前提是你已經照
> `integrations/sheets-orders/README.md` 建過那組「專用同步帳號」——這個工具
> **沿用同一組帳號**，不用再建一次）。
>
> 這份文件跟 `integrations/sheets-orders/README.md` 一樣，是給你自己看的
> 繁體中文操作手冊。系統本身的中文介面一律是簡體中文，那是給 SANCI 印尼
> 辦公室同事看的。

---

## 一、這個工具做什麼

你們現有的工作流程是：每來一筆訂單，就把「Sales Order (SO) - Updated」這個
分頁**複製一份**（連同 DO、Invoice 兩個分頁一起複製成一組三分頁），然後手動
把訂單內容一格一格打進 SO 分頁，DO 跟 Invoice 分頁靠公式自動算出來。

這個工具做的事情很單純：**你照舊複製分頁，複製完之後、開始手動打字之前**，
在 Apps Script 選單按一下，把系統裡某一筆訂單的資料**自動填進**剛複製出來、
還是空的那個 SO 分頁——省掉手動照著系統畫面一格一格抄的步驟。

操作方式：

1. 打開新複製出來、還沒填任何東西的 SO 分頁（分頁裡的 **P1 儲存格**應該顯示
   `No. SO`——這是工具用來確認「你現在真的打開的是 SO 分頁，不是 DO 或
   Invoice 分頁」的辨識依據）。
2. 上方選單 **SANCI** → **Isi dari sistem…**。
3. 第一個對話框：輸入**系統裡的訂單編號**（例如 `GH-CBR-260816-0012`，可以從
   系統的 Pesanan 列表畫面複製）。這是拿去系統查資料用的鑰匙，**必填**。
4. 第二個對話框：輸入**這張 SO 想用的文件編號**（No. SO，填進 Q1）。**可以
   留空**——留空就直接沿用第 3 步輸入的系統訂單編號當作 No. SO。
5. 工具去系統把這筆訂單的資料抓回來，填進 SO 分頁的輸入格（見下方「儲存格
   對應表」），最後跳出一個總結視窗：訂單編號、客戶名字、寫了幾行商品明細、
   有沒有任何警告。
6. **DO 跟 Invoice 分頁不用你管**——那兩個分頁 100% 是公式從 SO 分頁算出來
   的（已經對照過真正的試算表驗證過），SO 分頁填好，DO/Invoice 會自己跟著動。

## 二、這個工具**不做**什麼（很重要，先看完再用）

- ❌ **不會幫你複製分頁**。SO/DO/Invoice 三分頁一組的複製動作，還是照你們現在
  的做法手動複製。這個工具只負責「分頁複製好之後，把系統資料填進去」這一步。
- ❌ **不會寫 DO 或 Invoice 分頁的任何一格**。那兩個分頁完全靠公式讀 SO 分頁
  的資料自動算，工具只碰 SO 分頁。
- ❌ **不會把試算表上的任何修改寫回系統**。跟 `sheets-orders` 一樣，這是**單
  向**的：系統 → 試算表。你在 SO 分頁上手動改的任何字，系統完全不會知道。
- ❌ **不會建立新的 SO/DO/Invoice 分頁組**。要先手動複製出一組新的（跟現在
  一樣），工具才有分頁可以填。
- ❌ **不會列印或排版**。這個工具只負責把資料寫進儲存格，SO/DO/Invoice 要怎麼
  列印、要不要轉 PDF，都跟現有流程一樣，工具不插手。

## 三、安裝步驟

### 3-1 沿用 `sheets-orders` 的同步帳號

這個工具跟 `integrations/sheets-orders/` 用**同一組**「專用同步帳號」——不用
在 Supabase 再建一次帳號。如果你還沒設過那組帳號，先照
`integrations/sheets-orders/README.md` 的「第一步：建立一個『專用同步帳號』」
做完，再回來繼續下面的步驟。

如果你已經設過了：直接跳到 3-2。

### 3-2 把程式貼進「Form SO INV dan DO-SANCI」這份試算表

1. 打開你們現有的「Form SO INV dan DO-SANCI」試算表（**不是**新開一份——這個
   工具要跟你們現有的 SO/DO/Invoice 分頁在同一份試算表裡才有用）。
2. 上方選單 **擴充功能** → **Apps Script**。會開一個新分頁。
3. 如果這份試算表**還沒有**掛過任何 Apps Script：裡面預設有一個 `Code.gs`，
   內容大概是 `function myFunction() {}`，**把裡面的內容全部選起來刪掉**。
   如果這份試算表**已經**有別的腳本在跑：改用左側 **+** 新增一個檔案，命名
   隨意（例如 `SoFiller`），不要蓋掉既有的腳本。
4. 打開本資料夾裡的 `Code.gs`，**全選、複製、貼上**到剛剛準備好的地方。
5. 按上方的 💾 **儲存**圖示（或 Ctrl+S / ⌘+S）。

### 3-3 填四個設定值（跟 `sheets-orders` 完全一樣的四組）

1. 還在 Apps Script 畫面，左邊選單點 **專案設定**（⚙️ 齒輪圖示）。
2. 往下捲到 **指令碼屬性** 這一區 → 點 **新增指令碼屬性**。
3. 一組一組加進去，**總共四組**——直接從 `sheets-orders` 那個 Apps Script
   專案的「指令碼屬性」頁面**複製過來**就好，兩邊的值要完全一樣：

   | 屬性名稱（左邊，要一字不差） | 值（右邊） |
   |---|---|
   | `SUPABASE_URL` | 跟 `sheets-orders` 那個腳本的值一樣 |
   | `SUPABASE_ANON_KEY` | 跟 `sheets-orders` 那個腳本的值一樣 |
   | `SYNC_EMAIL` | 跟 `sheets-orders` 那個腳本的值一樣（`sheets-sync@...`） |
   | `SYNC_PASSWORD` | 跟 `sheets-orders` 那個腳本的值一樣 |

4. 按 **儲存指令碼屬性**。

> 🔒 **絕對不要**把 Supabase 的 **service_role** 那把鑰匙貼進來，理由跟
> `sheets-orders/README.md` 完全一樣——那把鑰匙是整個資料庫的萬能鑰匙，這個
> 工具完全用不到它。

**為什麼可以共用同一組帳號？** 這組同步帳號只是「登入身分」，它本身沒有寫入
權限——資料庫的規則（RLS）已經限制這個身分只能**讀**，兩個工具（`sheets-orders`
定時同步全部訂單清單、`sheets-so-filler` 手動查單一筆訂單細節）都是用它來讀，
不會互相干擾，也不需要為了「分開追蹤是誰做的」而多開一個帳號。

### 3-4 第一次執行的授權畫面

1. 回到試算表，**重新整理頁面**（F5）。上方選單列應該多出一個 **SANCI**。
2. 點 **SANCI** → **Isi dari sistem…**。
3. **第一次會跳出授權視窗**，這是正常的：
   - 跳出「需要授權」→ 按 **審查權限** → 選你自己的 Google 帳號。
   - 出現「Google 尚未驗證這個應用程式」的警告——正常情形（自己寫在自己
     試算表裡的腳本本來就會有這個警告），點左下角 **進階** → **前往
     「SoFiller」(不安全)** 之類的字樣。
   - 最後一頁列出它要的權限（讀寫這份試算表、連到外部網路），按 **允許**。
4. 授權完會直接繼續跑第一次的填單流程（見下方「四、使用方式」）。

## 四、使用方式

先照你們現在的做法，**複製出一組新的 SO/DO/Invoice 分頁**，打開那個新的 SO
分頁（P1 應該顯示 `No. SO`）。然後：

1. 上方選單 **SANCI** → **Isi dari sistem…**。
2. 對話框 1：輸入**系統裡的訂單編號**，按 OK。
3. 對話框 2：輸入**這張 SO 想用的文件編號**（可留空 = 沿用訂單編號），按 OK。
4. 如果這個分頁的 Q1 格**已經有別的值**（例如你打開了填過的舊分頁），工具會
   先跳出「確認要覆蓋嗎？」的視窗，選 **否** 可以安全中止，不會動到任何一格。
5. 跑完（通常幾秒鐘），跳出總結視窗：訂單編號、套裝名稱、客戶姓名、寫了幾行
   商品明細，以及（如果有的話）警告訊息列表。
6. 檢查一下 SO 分頁上的資料，DO 跟 Invoice 分頁應該已經自動算好了。**跟平常
   一樣做獨立核對**：挑一兩個數字對照系統畫面，不要看到資料出現就假設是對的。

**同一個 SO 分頁可以重複執行**——例如系統那邊資料改過、想重新拉一次。重新
執行會把 P15:X26 的商品明細**整批清空重寫**（不會有舊行殘留），Q/S 欄的
輸入格也會重新寫一次（S11「Nama Admin」除外，那格永遠不會被工具動到）。

## 五、儲存格對應表

### 5-1 表頭（Q 欄、S 欄）

| 儲存格 | SO 分頁欄位 | 資料來源 | 備註 |
|---|---|---|---|
| Q1 | No. SO | 對話框 2 輸入的文件編號（留空則用訂單編號） | |
| Q2 | Code Customer | **固定清空**（寫入空字串） | 系統沒有對應的客戶代碼；這格原本是拿去 XLOOKUP「Data Customer」分頁用的鍵，但 S1/S7/S8/S9 已經直接寫死成文字（見 5-2），不再依賴這格 |
| Q3 | TGL SO | 訂單的建立時間（`created_at`） | 寫入真正的日期，不是文字 |
| Q6 | Delivery By | **完全不碰** | 系統沒有對應欄位（見「六、已知邊界」） |
| Q7 | Discount 1 | `discount_pcts[0]` | 折扣鏈第 1 段（百分比數字，不是小數） |
| Q8 | Discount 2 | `discount_pcts[1]` | 折扣鏈第 2 段 |
| Q9 | Discount 3 | `discount_pcts[2]` | 折扣鏈第 3 段；系統最多可以有 6 段，模板只有 3 格（見「六、已知邊界」） |
| Q10 | TGL DP | **完全不碰** | 系統只存 DP 金額，沒存 DP 的日期 |
| Q11 | DP Amount | `order_sanci_offers.dp_amount` | |
| Q12 | Conditions Payment | `order_sanci_offers.payment_condition` | 自由文字 |
| Q13 | Noted | 訂單的 `notes`，加上（如果有）Markup／現金折讓的附註 | 見「六、已知邊界」 |
| S1 | 客戶姓名 | `customers.full_name` | **固定改成文字**，不再是公式 |
| S7 | 客戶電話 | `customers.phone_normalized`（轉成 `0812-3456-789` 這種本地格式），沒有的話用原始 `phone` | 同上 |
| S8 | 客戶 Email | **固定清空** | 系統沒有存客戶 Email |
| S9 | Alamat Kirim Barang | 這筆訂單自己的 `shipping_address`；是空的就用客戶主檔的 `alamat、kota、provinsi` 拼起來 | 同上 |
| S10 | Alamt Kirim Doc | **完全不碰** | 系統沒有對應欄位 |
| S11 | Nama Admin | **完全不碰**（永遠不讀也不寫，即使是空的） | 操作的人自己打自己的名字 |
| S12 | Nama Sales | 這筆訂單的業務員姓名（`partner_sales_staff_id` → `partner_staff.full_name`） | 沒有指定業務員就留空 |
| S13 | Delivery Note | 依訂單的 `fulfillment_path` 換成一句話——「直接送貨」或「客戶自己來門市看貨/取貨」的說明，文字取自系統畫面本身用的同一句話 | |

### 5-2 商品明細（P15:X26，最多 12 行）

每次執行都會**先把 P15:X26 整塊清空**，再依訂單的 `order_items`（照建立時間
排序）逐行寫入，最多寫 12 行：

| 欄 | SO 分頁欄位 | 資料來源 |
|---|---|---|
| P | 產品代碼 | `code_snapshot`——有代碼的話，你們的 B/E 欄公式會照代碼 XLOOKUP 出品名。**沒有代碼的手動項目，這格留空** |
| Q | Custom Size | `custom_size` |
| R | Note | `note`；**沒有產品代碼的手動項目**，會把 `name_snapshot`（品名）接在最前面，讓這行看得出是什麼東西，不是一行空白備註 |
| S | Code Warna | `color_code` |
| T | Custom Price/Unit | `unit_price`（沒填就留空） |
| U | Manual Disc | `line_discount`（沒填就留空） |
| V | Qty | `quantity` |
| W | Pack QTY | **固定留空** — 系統沒有對應欄位 |
| X | Pack/Bag | **固定留空** — 系統沒有對應欄位 |

**完全不碰**：A 到 N 欄（公式鏡射欄）、第 27 列以後（合計公式）、DO 分頁、
Invoice 分頁、其他任何分頁。

## 六、已知邊界（設計上就是這樣，不是漏做）

- **一次只能填一筆訂單**。跟 `sheets-orders`（每 15 分鐘整批同步所有訂單）不
  一樣，這個工具是給「正在手動處理一張 SO」的當下用的，一次一筆。
- **商品明細最多 12 行**。訂單超過 12 個品項時，工具只會寫前 12 行，多出來的
  會被跳過，並且在完成後的總結視窗清楚列出**哪幾行被跳過**（品名），不會靜
  悄悄漏掉。這是 SO 模板本身 P15:X26 的物理限制，不是工具的 bug。
- **折扣鏈最多 3 段（Q7/Q8/Q9）**。系統的折扣鏈（`discount_pcts`）最多可以
  設定 6 段，但 SO 模板只留了 3 個折扣格。超過 3 段時，工具只填前 3 段，並在
  總結視窗警告「還有幾段沒填」——這種情況下 SO 分頁自己算出來的合計，跟系統
  裡 `final_amount` 顯示的最終金額**會對不起來**，要另外去系統核對真正的
  折扣鏈。
- **Markup／現金折讓沒有自己的儲存格**。SO 模板本身沒有設計「加成」跟「現金
  折讓」這兩個欄位的位置，工具會把它們寫成一句話附加在 Q13（Noted）的最後
  面，並在總結視窗提醒你「這裡有東西被塞進備註欄」。要看精確數字，還是要回
  系統的訂單詳情頁確認。
- **Q6「Delivery By」完全不填**。盤點系統欄位時，找不到任何一個欄位明確對應
  這格的意思（不是分店、不是業務員、也不是配送方式）——寧可完全不碰，讓你
  照舊手動填，也不要瞎猜寫一個可能誤導人的值進去。如果 Jenzo 確認這格其實
  該對應到某個系統欄位（例如分店名稱），之後可以再補上映射。
- **Q2「Code Customer」固定清空，不會有值**。原因見上面的儲存格對應表——
  系統沒有這種代碼，而且 S1/S7/S8/S9 已經直接寫死不再依賴這格做 XLOOKUP，
  所以清空它不影響任何東西算出來的結果。
- **明細只有 migrasi 0014 之後建立的訂單才有**。`order_items`
  這張表是 `0014_permissions_items_shipping.sql` 才新增的。在那之前建立的
  舊訂單，系統裡根本沒有逐行的商品明細資料——工具會照樣把表頭資料填好，
  但 P15:X26 會是空的（總結視窗會用一句話說明原因，不是靜悄悄留空）。
- **SO 分頁自己算出來的合計，可能跟系統看到的 `Harga Akhir` 不一樣**。SO 模板
  的合計是**它自己的公式**（明細單價 × 數量，再套用 Q7/Q8/Q9 三個折扣格）
  算出來的，跟系統資料庫用 `discount_pcts`/`markup_pct`/`cash_discount` 算出
  來的 `final_amount` 是**兩條獨立的計算路徑**。兩者在「折扣只有 1–3 段、
  沒有 Markup、沒有現金折讓」的情況下應該一致；一旦用到 Markup 或現金折讓
  （沒有對應欄位，見上面），或折扣超過 3 段，兩邊的數字就會對不起來——
  **以系統畫面上的 `Harga Akhir` 為準**，SO 分頁的合計只是給列印用的呈現。

## 七、疑難排解

| 症狀 | 原因 | 怎麼修 |
|---|---|---|
| 選單列沒有出現「SANCI」 | 頁面還沒重新載入，或 `Code.gs` 沒存到 | 重新整理試算表頁面（F5）。還是沒有的話回 Apps Script 確認檔案有存 |
| 跳出「Tab aktif ... sepertinya bukan tab Sales Order (SO)」 | 目前打開的分頁不是 SO 分頁（P1 不是 `No. SO`），可能開到 DO/Invoice 分頁，或分頁格式跟模板不一樣 | 切到正確的 SO 分頁再執行一次 |
| 跳出「Nomor pesanan tidak ditemukan di sistem」 | 訂單編號打錯，或系統裡真的沒有這筆訂單 | 回系統 Pesanan 列表核對正確的訂單編號，直接複製貼上比手打保險 |
| 跳出「Login akun sync GAGAL (HTTP 400 / 401)」 | 四個指令碼屬性其中一個打錯 | 回 3-3 重新確認，最保險的做法是直接從 `sheets-orders` 的指令碼屬性頁面複製貼過來 |
| 跳出「Script Property belum diisi: ...」 | 後面列出來的那幾格還沒填 | 回 3-3 補齊，名稱要一字不差（全大寫、底線） |
| 執行完但只有表頭有資料，商品明細是空的 | 這筆訂單是 migrasi 0014 之前建立的舊訂單（系統裡沒有逐行商品資料），或 0014 根本還沒在這個資料庫執行過 | 正常現象（見「六、已知邊界」），舊訂單本來就沒有這份資料可抓，商品明細只能照舊手動打 |
| 總結視窗說「還有幾行被跳過」 | 這筆訂單品項超過 12 行，模板裝不下 | 手動把多出來的品項另外處理（例如加開一組新的 SO，或跟 Jenzo 討論模板要不要加行） |
| 總結視窗說「還有幾段折扣沒填」 | 系統這筆訂單的折扣鏈超過 3 段，模板只有 3 格 | 回系統訂單詳情頁核對完整折扣鏈，SO 分頁自己算出來的合計這時候不能直接信 |
| Q13（Noted）看起來多了一段「Markup .../ Potongan tunai ...」 | 這筆訂單有系統的加成或現金折讓，模板沒有專屬欄位可以放 | 正常現象，去系統訂單詳情頁核對精確數字 |
| 跳出「確認要覆蓋嗎？」但我沒印象填過這分頁 | 這個 SO 分頁的 Q1 已經有別的文件編號了（可能是複製別人填過的分頁，或這個分頁本來就不是全新的） | 先確認清楚這個分頁到底屬於哪筆訂單，再決定要不要按「是」覆蓋 |
| 重跑一次之後商品明細變少了 | 每次執行都會先把 P15:X26 整塊清空再重寫——這是設計上的行為（避免舊分頁殘留的資料混進新資料），不是漏資料 | 屬於正常行為；如果懷疑系統那邊資料本身有問題，回系統訂單詳情頁核對 |

## 八、安全須知

跟 `integrations/sheets-orders/README.md` 完全一樣（同一組帳號、同一套風
險）：這組同步帳號**只能讀**，一行程式都不會往系統裡寫東西。

| 情況 | 該怎麼辦 |
|---|---|
| 這份試算表不小心分享給不該看的人 | ① 先把試算表的分享權限收回；② 到 Supabase → Authentication → Users 找到 `sheets-sync@...` → 右邊三個點 → **Delete user**（或先改密碼）。**這會同時停掉 `sheets-orders` 的定時同步**，因為兩個工具共用同一組帳號——重新做一次帳號設定，兩邊都會恢復 |
| 懷疑密碼外流 | 到 Supabase 把那個同步帳號的密碼改掉，然後**兩個 Apps Script 專案**（`sheets-orders` 跟這個）的指令碼屬性都要把 `SYNC_PASSWORD` 換成新的——漏改一邊，那邊就會開始跳登入失敗 |
| 有人問你要 service_role key | 不要給，也不要貼進這個工具。這個工具完全用不到它 |
